- **Scope and date:** Research checked **November 11, 2026**. This is a comparison of published documentation and user reports; HybridPipPlayer itself was not tested. Undated sources use this access date. No files were modified.

- **Most useful comparison projects:** [mpv.net](https://github.com/mpvnet-player/mpv.net) for Windows/libmpv integration; [asbplayer](https://docs.asbplayer.dev/docs/compatibility/) for streaming-site subtitle adapters; [OnTopReplica](https://github.com/LorenzCK/OnTopReplica) for native window behavior; and [PiP+](https://pipext.app/support) for Document PiP, captions, controls, and danmaku. These cover different parts of HybridPipPlayer’s design rather than providing one equivalent product.

- **DRM: WebView2 must not be treated as Edge with identical streaming support.** The WebView2 Widevine feature request remains open. It was filed **September 21, 2024**, with Microsoft responding **November 22, 2024**; it is not evidence of delivered Widevine support. Consequently, “Widevine L3 versus L1 in WebView2” starts with an unproven prerequisite: an available, supported Widevine implementation. **NEEDS VERIFICATION:** Netflix and Disney+ playback in the exact WebView2 runtime shipped with the app. [WebView2 issue #4828](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4828)

- **PlayReady also has deployment-specific pitfalls.** A WPF application reported protected playback failing with Fixed Version runtime **123.0.2420.81**, while Evergreen worked; the issue was opened **June 15, 2024**, and that distinction was confirmed by the reporter on **June 17**. The issue remains open, but this historical report does not establish that every current Fixed Version runtime fails. **NEEDS VERIFICATION:** Evergreen versus Fixed Version, GPU/driver combinations, and actual service playback. [WebView2 issue #4632](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4632)

- **Do not publish a universal “L3 means 480p, L1 means 4K” rule.** Google’s L1/L3 provisioning guidance is explicitly about Android devices; it does not establish WebView2 capabilities or service resolution policies. Netflix currently lists **up to 2160p for both Windows Chrome and Edge**, subject to its Ultra HD requirements. Those browser limits do not transfer automatically to an embedded WebView2 application. [Google Widevine guidance](https://support.google.com/widevine/answer/6072714?hl=en), [Netflix browser requirements](https://help.netflix.com/en/node/30081) — checked **November 11, 2026**.

- **Disney+ browser quality is a separate service restriction.** The indexed UK help article states computer browsers are limited to **720p**, with no browser 4K. Direct retrieval returned no readable article body during this research. **NEEDS VERIFICATION:** the current cap for the target country, account, browser, and WebView2 configuration; do not promise 1080p/4K based on display size or decoding capability. [Disney+ data usage and quality](https://help.disneyplus.com/en-GB/article/disneyplus-en-gd-data-usage) — indexed article dated approximately **July 2026**, checked **November 11, 2026**.

- **Document PiP has deliberate limits that native WPF windows can differentiate against.** Chrome requires a user gesture; the PiP window cannot navigate, cannot outlive its opener, and cannot have its screen position set by the website. Requested dimensions may be clamped. Custom controls and captions are supported use cases, but precise native snapping and independent window lifetime are outside this model. [Chrome Document PiP documentation](https://developer.chrome.com/docs/web-platform/document-picture-in-picture) — checked **November 11, 2026**.

- **All-frame injection does not make Document PiP callable from every iframe.** The API is available only to the top-level traversable, although its window may contain cross-origin iframes. The specification permits only one Document PiP window per opener; whether multiple openers can maintain simultaneous PiP windows is implementation-dependent. Plan a top-frame coordinator and frame messaging. **NEEDS VERIFICATION:** preserving user activation through the chosen cross-frame flow. [Document PiP draft, February 4, 2026](https://wicg.github.io/document-picture-in-picture/)

- **MV3 `all_frames` means all matching frames—not unrestricted access everywhere.** Frame URLs must match; `about:blank`, `data:`, and `blob:` frames require the appropriate related-frame options. Content scripts normally run in isolated worlds, so access to a `<video>` element does not expose a site’s private JavaScript player objects. Use per-frame discovery, deduplication, and explicit adapters rather than assuming one top-document scan is sufficient. [Chrome content-script documentation](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts) — checked **November 11, 2026**.

- **“Detected a video” and “can export its playback” are different capabilities.** Asbplayer maintains dedicated subtitle integrations and documents generic detection as best effort; Amazon Prime timing can be offset, and some tracks require selection in the original player first. HybridPipPlayer should similarly distinguish detection, playback control, subtitle access, and external playback eligibility. **NEEDS VERIFICATION:** each service’s subtitle representation and behavior when its video/player DOM is moved. [Asbplayer compatibility](https://docs.asbplayer.dev/docs/compatibility/) — checked **November 11, 2026**.

- **MV3 background state is disposable.** Chrome normally terminates an extension service worker after **30 seconds of inactivity**, with documented exceptions. Persist essential state and reconnect controls after worker restarts. Native messaging is unavailable directly to content scripts: route through an extension page or service worker, validate the sender, and sanitize payloads before invoking the Windows application. [Service-worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle/), [Native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) — checked **November 11, 2026**.

- **libmpv + yt-dlp requires ongoing compatibility work.** Full YouTube support gained an external JavaScript-runtime requirement in **yt-dlp 2025.11.12**, alongside its EJS component. The EJS guide, edited **July 12, 2026**, requires compatible component versions. This adds another dependency beyond `libmpv.dll` and `yt-dlp.exe`. Ship a tested dependency set, explicit executable paths, actionable diagnostics, and a rollback-capable updater. [Upstream announcement](https://github.com/yt-dlp/yt-dlp/issues/15012), [EJS setup guide](https://github.com/yt-dlp/yt-dlp/wiki/EJS)

- **A successful yt-dlp extraction does not guarantee successful mpv playback.** An **October 27, 2026** mpv discussion reports YouTube playback returning HTTP 403 after a yt-dlp update. This establishes a real integration failure report, not its universal cause. Test extraction and playback separately, including seeking and resumed playback; redact signed media URLs and authentication data from diagnostics. [mpv discussion #18702](https://github.com/mpv-player/mpv/discussions/18702)

- **Chrome Web Store risks concern permissions, behavior, and claims—not merely touching streaming sites.** Policies require narrow permissions, a clear single purpose, and disclosed handling of user data. They also prohibit extensions whose sole purpose is launching another application; the extension’s own playback/subtitle functionality therefore matters. `<all_urls>` needs a concrete justification. Prefer optional per-site access where practical, and avoid claiming universal streaming compatibility. Store approval remains **NEEDS VERIFICATION**. [Chrome Web Store policies](https://developer.chrome.com/docs/webstore/program-policies/policies?hl=en) — checked **November 11, 2026**.

- **Remote adapter fixes have an MV3 distribution constraint.** Downloaded executable JavaScript or WASM is remotely hosted code; ordinary JSON/CSS is treated differently. Keep extension logic packaged and reviewed rather than downloading executable site adapters as an emergency update mechanism. The native application’s updater is a separate distribution surface. [Chrome remotely hosted code guidance](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code) — checked **November 11, 2026**.

- **Streaming terms create meaningful wrapper and automation risk.** Netflix’s terms, updated **April 10, 2026**, restrict automated access and interference with protection mechanisms, its interface, and advertising. Disney’s published **October 17, 2025** agreement restricts automation, unauthorized framing/embedding, modification, and circumvention. Successful playback does not establish contractual permission. **NEEDS VERIFICATION:** the current agreement in each launch jurisdiction and how specific controls, subtitle injection, and commercial distribution are treated. [Netflix terms](https://help.netflix.com/legal/termsofuse), [Disney agreement archive](https://www.disneyplus.com/welcome/subscriber-agreement)

- **mpv licensing depends on the actual build.** Upstream defaults to **GPLv2-or-later**; an LGPL-compatible build excludes GPL-only files, with `-Dgpl=false` offered as a convenience—not a complete compliance guarantee. Audit FFmpeg and other dependencies too. Linking a proprietary WPF app against an arbitrary downloaded `libmpv.dll` is not a safe licensing assumption. **NEEDS VERIFICATION:** the shipped DLL’s provenance, build configuration, source obligations, and application-license compatibility. [mpv copyright and build-license rules](https://github.com/mpv-player/mpv/blob/master/Copyright) — checked **November 11, 2026**.

- **yt-dlp’s Unlicense does not describe every distributed executable.** Its repository and Python distributions contain Unlicense code, but upstream says PyInstaller-bundled executables include **GPLv3+** code and the combined executable is GPLv3+. Redistributing that executable requires evaluating those obligations; launching it as a subprocess does not automatically settle the licensing of the entire product. [yt-dlp licensing section](https://github.com/yt-dlp/yt-dlp#licensing) — checked **November 11, 2026**.

- **Recurring complaint: captions suddenly disappear after a site change.** Asbplayer issue #711, opened **May 8, 2025**, contains multiple reports of YouTube subtitles disappearing and auto-pause failing; a contributor observed an HTTP 200 response with empty subtitle data. This supports maintaining service-specific regression cases and clear subtitle-failure messages. It does not prove the defect remains present today. [Asbplayer issue #711](https://github.com/asbplayer/asbplayer/issues/711)

- **Recurring complaint: window behavior has small but disruptive edge cases.** OnTopReplica issue #184, opened **October 31, 2025**, reports that its top 4–5 pixels still intercept input in click-through mode. Asbplayer separately documents shortcut conflicts, zoom-sensitive screenshot cropping, and interference from other extensions. Treat these as useful test cases, not measured prevalence. [OnTopReplica issue #184](https://github.com/LorenzCK/OnTopReplica/issues/184), [Asbplayer troubleshooting](https://docs.asbplayer.dev/docs/common-issues/)

- **Community corroboration:** A Reddit report dated **January 2, 2026** describes mpv/yt-dlp playback starting at an unexpected timestamp; another dated **June 9, 2026** describes links loading without playback despite updates. These are anecdotes, but they suggest visible resume-state controls and error reporting would address recognizable frustrations. [Unexpected start position](https://www.reddit.com/r/mpv/comments/1q1qnsb/issues_streaming_youtube_via_mpv_and_ytdlp/), [YouTube links failing](https://www.reddit.com/r/mpv/comments/1u10am8/help_dragging_youtube_links_in_mpv_does_not_work/)

- **Differentiator 1 — Dual-track subtitle workspace:** Borrow asbplayer’s simultaneous tracks, independent styling, timing adjustment, and subtitle navigation. Add bilingual captions and a searchable transcript to HybridPipPlayer’s existing appearance controls. **NEEDS VERIFICATION:** track access on each streaming service. [Asbplayer settings](https://docs.asbplayer.dev/docs/reference/settings/) — checked **November 11, 2026**.

- **Differentiator 2 — Sentence-based practice mode:** Adopt subtitle-boundary auto-pause and repeat, with repeat counts and an optional reveal-after-listening mode. Expose large controls in the remote window so this is usable without precise timeline interaction. [Asbplayer recipes](https://docs.asbplayer.dev/docs/guides/recipes/) — checked **November 11, 2026**.

- **Differentiator 3 — Saved crop presets:** Borrow OnTopReplica’s stored subregions and relative coordinates to offer reusable lecture, sports, or ultrawide framing presets. Apply cropping within supported playback paths; protected-content compatibility is **NEEDS VERIFICATION**. [OnTopReplica features](https://github.com/LorenzCK/OnTopReplica#readme) — checked **November 11, 2026**.

- **Differentiator 4 — Searchable, remappable controls:** Borrow mpv.net’s searchable configuration/input editors, configurable menus, and global shortcuts. Map the same commands to large remote-control buttons, with a dependable command to exit click-through mode. [mpv.net features](https://github.com/mpvnet-player/mpv.net#features-exclusive-to-mpvnet) — checked **November 11, 2026**.

- **Differentiator 5 — Explainable compatibility and recovery:** Adapt asbplayer’s explicit compatibility matrix and troubleshooting model into an in-app status panel: selected engine, dependency versions, available subtitle tracks, and the failed playback stage. Offer supported-browser handoff when embedded playback fails. This is a proposed synthesis, not a feature claimed by those projects; its value is making partial support understandable. [Asbplayer compatibility](https://docs.asbplayer.dev/docs/compatibility/), [mpv integration failure report, October 27, 2026](https://github.com/mpv-player/mpv/discussions/18702)
